# RecallMate Password + Email Step-Up Authentication — Design

**Status:** Revised per security review; pending re-approval for implementation planning. No implementation is authorized.
**Date:** 2026-09-28

## Goal

Replace RecallMate's current passwordless email sign-in with password-based email accounts and require a fresh, RecallMate-managed email verification code on every new interactive login, including Google OAuth. A user may reach normal RecallMate data only after primary authentication, the required email step-up, and (when needed) controlled account enrollment have all succeeded.

“Every login” means a new authentication event after logout, session expiry/revocation, or a new browser/device login. Ordinary navigation, page refresh, tab reopen with the same valid session, and token refresh do not send another code.

The application must not release a usable Supabase session to the browser before the applicable email verification is complete. A Supabase Auth session may exist server-side while pending; it is not an authorized RecallMate session until the claim and server-side session record agree.

## Decision summary

- Email signup creates a password at signup and uses Supabase's signup-confirmation code as the initial email-possession check.
- Existing email sign-in validates email and password server-side, then sends a separate RecallMate-generated six-digit code.
- Google OAuth remains a primary identity method, followed by the same RecallMate-generated code sent to the verified account email.
- `signInWithOtp()` is not used as the second step. Supabase email OTP is a passwordless sign-in method whose verification creates a Supabase session; it cannot serve as this design's login challenge. See [Supabase Passwordless Email](https://supabase.com/docs/guides/auth/auth-email-passwordless).
- The custom email step-up is not represented as Supabase `aal2`. Supabase's native MFA flow documents TOTP and phone factors; `aal` remains the value Supabase actually issued. See [Supabase MFA](https://supabase.com/docs/guides/auth/auth-mfa).
- A custom access-token claim, `rm_login_verified`, is derived from a server-maintained record for the exact Supabase `session_id`. It is never sourced from editable `user_metadata`.
- A separate server-only account-enrollment record is required in addition to a verified session. A direct Supabase Auth signup or first-time OAuth account is not a RecallMate-enrolled account and gets no private app access until username/profile readiness and current legal consent are finalized by RecallMate.
- RLS, Storage policies, Realtime, RPCs, and service-role routes enforce this boundary. Hiding a page or removing a button is not authorization.
- The step-up claim protects RecallMate application data and RecallMate-controlled routes, not every operation exposed by Supabase Auth's public control plane. That residual boundary is explicit below; platform Auth settings and direct-API tests are required.
- Recovery sessions are restricted to password recovery and never receive normal RecallMate access.
- Existing OTP-only accounts retain their user IDs and data. They must establish a password through recovery before email/password login; Google-linked users can continue with Google plus step-up.

## Terminology and assurance

- **Primary authentication:** Supabase email/password or Google OAuth.
- **Signup confirmation:** Supabase's initial email code after creating an email/password account.
- **Email step-up:** A one-time code generated and verified by RecallMate after a successful password or Google login.
- **Pending session:** Supabase session material held server-side and encrypted while email verification is pending. It is not placed in browser storage or cookies.
- **Verified session:** A Supabase `session_id` with an active server-side verification record and a refreshed JWT containing `rm_login_verified: true`. It authorizes RecallMate access only while the separate account-readiness record remains `ready`.

Email possession is a weaker step-up than a separately enrolled authenticator because mailbox access may be the same recovery channel as the account email. Product copy must say “email verification” or “email step-up,” not claim Supabase MFA/AAL2. Users needing stronger assurance should be considered for a separate native TOTP project.

## Scope

This design covers signup, password sign-in, Google sign-in, challenge delivery and verification, session issuance and refresh, authorization enforcement, logout, password recovery/change, account migration, and acceptance testing.

It does not authorize a production Supabase mutation, Vercel deployment, or broad unrelated database cleanup. The hosted Supabase signup-confirmation template must use `{{ .Token }}` for numeric signup verification. The separate login step-up email is generated by RecallMate through a server-only mail provider. Current hosted template state must be verified in a non-production environment before release.

## Existing repository boundary

Read-only inspection of the Task 2 worktree found:

- `components/auth/EmailOTPForm.tsx` currently calls `signInWithOtp()` for both signup and sign-in, and verifies the code in the browser.
- `app/(onboarding)/onboarding/page.tsx` does not set or update a password. It currently updates username/completion flags in editable Auth user metadata; those flags are not authoritative enrollment evidence and must not satisfy the readiness gate.
- `app/auth/callback/route.ts` exchanges the Google authorization code through the cookie-backed Supabase server client. That currently crosses the session-cookie boundary before a new email step-up.
- `middleware.ts` refreshes the Supabase session but does not require a RecallMate verification claim.
- `app/(app)/layout.tsx` accepts a valid Supabase JWT without checking a RecallMate step-up claim or active verification record.
- The callback also supports `integration=google-calendar`. Calendar linking is a separate integration flow, not a new RecallMate login; it must remain distinct and must not be accidentally forced through or used to bypass the login challenge.
- `app/api/auth/check-availability/route.ts` intentionally returns username availability but not email existence. Its process-local rate limit is not sufficient for production challenge abuse control.
- `public.profiles` exists and is client-writable under owner RLS; `username` is synchronized from editable Auth user metadata. Signup currently stores `privacy_agreed` in user metadata. The inspected local migrations contain no authoritative, append-only legal-consent store or server-only account-readiness record. Therefore `profiles` remains the profile projection, while account readiness and consent need a server-only authoritative record unless a wider migration audit finds an existing audited consent system. Neither username-shaped metadata nor `privacy_agreed` metadata may authorize access.
- `@upstash/redis` and `@upstash/ratelimit` are already dependencies, but current app rate-limit code includes in-memory implementations. Their production configuration must be verified before relying on them.

These findings make this a cross-boundary auth change. The auth form alone is not an adequate implementation target.

## Authentication flows

### Email/password signup

1. Signup collects username, email, password, confirm password, and required Privacy/Terms acknowledgement (unchecked by default). Password input supports paste and password managers; minimum length is 12 characters, with no arbitrary character-composition rule.
2. A server endpoint validates the strict request and stores the accepted Privacy/Terms versions and timestamp as a short-lived, unbound pending enrollment intent. This is flow evidence, not yet a finalized consent event. Before Auth creation, the server generates a flow-specific, high-entropy creation-correlation value and stores a keyed digest plus authenticated ciphertext needed for same-flow retry. It calls Supabase `signUp(email, password)` with email confirmation required and carries the correlation through a provider-supported server-initiated creation field (the candidate is a dedicated non-authoritative Auth user-metadata property). This value is correlation only: it is never an authorization claim or readiness evidence. The server may classify a request as `created` and bind intent only after the non-production provider contract proves that the exact returned Auth user ID resolves and its correlation matches this exact parent flow, while duplicate confirmed/unconfirmed requests cannot inherit or overwrite that flow's correlation. A non-null `user.id`, successful `getUserById()`, email match, timestamp match, or apparent success alone is insufficient. Duplicate results never bind; indeterminate results never bind and retain only an expiring unbound intent for safe same-flow retry/recovery. If the provider cannot prove this contract, signup creation stops for a design decision rather than binding by guesswork. The route returns the same status, response shape, and neutral copy for fresh creation, confirmed/unconfirmed duplicate, and indeterminate outcomes; it never returns a `created`/duplicate indicator or otherwise reveals account existence. Only an exact-flow-correlated creation is bound or allowed to proceed to signup OTP verification. Final immutable consent events and readiness are committed only after email confirmation. The database remains authoritative for username uniqueness.
3. Signup state and pending enrollment intent are durable across serverless instances and bound to a stable parent auth-flow record through an opaque, short-lived HttpOnly flow cookie. The cookie resolves the parent flow, never a child challenge. Email and `next` are not put in the URL; `next` is normalized with the existing safe internal-path helper. Retries within that exact parent flow reuse its persisted correlation value; a different flow gets a different value. After exact-ID correlation verification succeeds, persist the returned `user_id` into that intent and consume the correlation material idempotently. If the Auth result is indeterminate, do not bind by email or user existence and do not call signup OTP verification; preserve only an expiring unbound intent or use the documented safe recovery path.
4. Supabase sends the signup-confirmation code using the confirmation template containing `{{ .Token }}`. The signup intent stores no recoverable plaintext email. For verification, the server uses the exact `user_id` already bound to the flow and a server-only `auth.admin.getUserById(user_id)` lookup to obtain the canonical Auth email. It requires the returned user ID to match and a usable canonical email; lookup failure fails closed. The browser-supplied email and keyed email digest are never used as verification authority, and the server never searches Auth users by email to recover or bind an account. The server verifies with the installed Supabase SDK's signup-confirmation OTP mode using that canonical email and submitted token; the exact `verifyOtp` type is pinned by a non-production integration test, not guessed from the email-login flow.
5. Signup confirmation creates a Supabase session only in server memory. One database transaction finalizes the RecallMate profile, append-only consent events, `account_readiness.status = 'ready'`, and that session's verified-session row. Immediately afterward, the server forces refresh and validates the refreshed JWT, then writes normal Supabase SSR session cookies. If enrollment cannot be completed, it creates no verified-session row and returns no normal session cookie; the flow remains restricted until controlled enrollment completes.
6. Onboarding may collect any remaining profile fields but never creates or changes a password. A user cannot reach ordinary onboarding APIs or private app data until the account-enrollment completion transaction succeeds; any pre-enrollment screen is a narrowly scoped unauthenticated server flow bound to the stable parent-auth-flow cookie.

For an unready account that has completed email step-up, enrollment may consume `stepup_verified_at` only while the same parent flow is unexpired and unrevoked, the pending session still matches the exact stored `user_id` and `session_id`, and the step-up evidence is no more than 10 minutes old. Expired/revoked evidence destroys pending session secrets and requires fresh primary authentication and email step-up; no stale proof may finalize enrollment.

Hosted email confirmation must remain enabled. If the project is configured to auto-confirm signup and returns a session before email verification, the server flow must not issue that session to the browser and must fail closed until the confirmation contract is restored.

### Account enrollment and readiness

- Supabase Auth account existence is not proof of RecallMate enrollment. Any Auth user with no authoritative readiness row—including direct/public Auth signups, first-time Google users, legacy OTP-only users, and accounts created outside RecallMate—has `enrollment_required` and cannot receive `rm_login_verified: true`, pass the database helper, or pass `requireVerifiedRecallMateSession()`.
- The readiness record is private, server-owned, keyed by `user_id`, and distinct from `public.profiles`. It becomes `ready` only after a trusted flow has established a valid unique username/profile, current Privacy/Terms acceptance, and the required primary identity/email verification. Auth user metadata and client profile writes cannot create or upgrade this record.
- Legal consent is recorded as append-only versioned events (Privacy version, Terms version, accepted timestamp, and flow/source reference) bound to the actual `user_id` only after Auth creates that account. The readiness row refers to the required current consent versions; publishing a new legal version atomically marks affected readiness rows `policy_reaccept_required` until a new event is recorded. The unbound pre-signup intent is short-lived, server-only, and never counted as finalized consent.
- First-time Google and externally/direct-created accounts may complete a restricted enrollment flow after primary authentication and email step-up, but the pending Supabase session remains server-side. Successful step-up is recorded on the parent flow as `stepup_verified_at` while readiness is not `ready`; it does not create a verified-session row. The enrollment transaction collects/validates username and current consent, commits profile + consent + readiness=`ready` + the verified-session row atomically, then forces token refresh, validates the verified claim, and only then issues normal cookies. No normal app session is issued partway through enrollment.
- Existing users are not auto-enrolled from `user_metadata`, `public.profiles` alone, or an unverified historical flag. A reviewed migration must classify users using authoritative consent evidence; users without it enter `enrollment_required` and re-accept current legal terms. Existing OTP-only users keep their user IDs/data and establish a password through recovery before the normal password + email-step-up path. Existing Google users continue with Google plus step-up, then complete enrollment if required.

### Email/password sign-in

1. The browser posts only email, password, and the sanitized destination to a server endpoint over HTTPS. The request is strict; client-supplied user IDs, verification status, claims, or tokens are rejected.
2. A server-only Supabase client with session persistence disabled calls `signInWithPassword()`. Wrong email/password responses remain generic and do not reveal account existence.
3. On successful primary authentication, the server extracts and validates the returned user ID and `session_id`, encrypts the refresh token with authenticated encryption, and stores it in a durable pending challenge record. No Supabase session cookie or token is returned to the browser.
4. RecallMate generates and sends a fresh six-digit code through the server-side auth-mail adapter. The response indicates that verification is required without exposing provider or account details.
5. After code verification, one transaction atomically consumes the active child challenge. If account readiness is already `ready`, the same transaction inserts the verified-session row for that exact user/session pair; the server then refreshes the pending Supabase session, validates the refreshed JWT, and only then writes normal Supabase SSR session cookies. If readiness is not `ready`, the transaction records `stepup_verified_at` and the parent flow state `stepup_verified_pending_enrollment`, but creates no verified-session row. The session remains server-side and no normal cookie is issued until the controlled enrollment transaction commits readiness and the verified-session row together.

### Google sign-in

1. Google OAuth starts with PKCE and a short-lived server-controlled flow bound to a sanitized `next` destination.
2. The callback exchanges the code without persisting Supabase session cookies. The PKCE verifier is consumed from the login flow; the resulting session stays server-side and is encrypted as pending state.
3. The callback requires a usable, verified account email from the authenticated Supabase user. It sends the same RecallMate six-digit step-up challenge as password sign-in.
4. If the user is already enrolled, only successful challenge, refreshed-claim validation, and normal SSR cookie issuance complete app login. If not, successful challenge consumption records `stepup_verified_at` on the parent flow but creates no verified-session row; the pending session remains server-side while the user completes the restricted username/consent enrollment flow. The enrollment transaction then commits profile + consent + readiness=`ready` + verified-session row atomically; only after refresh and claim validation are normal cookies set.

The `google-calendar` integration callback remains separate: it requires an already verified RecallMate session, preserves its existing provider-token/calendar behavior, and must not replace or elevate the current app session. It does not trigger a fresh login challenge merely because a user links Calendar.

### RecallMate email-step-up challenge lifecycle

- This lifecycle applies only to RecallMate-generated email-step-up challenges after password or Google primary authentication. Each code is cryptographically generated with six digits, expires after 10 minutes, allows at most five incorrect attempts per challenge, and has a 60-second resend cooldown.
- Supabase-managed signup confirmation is a separate provider-owned flow. Supabase Auth determines that OTP's length, expiry, attempt limits, resend behavior, and verification semantics from its project configuration and provider implementation. RecallMate tracks only signup-flow state and the exact Auth identity/correlation; it does not generate, hash, count attempts for, expire, or promote the Supabase OTP as though it were a six-digit RecallMate challenge. The non-production spike pins the configured length and provider behavior, and the signup UI accepts that configured length.
- RecallMate resend creates a replacement child-challenge identity and code under the same stable parent auth flow. The old app-generated code remains valid only while replacement delivery is pending; successful provider acceptance atomically promotes the replacement as the parent's active challenge and supersedes the old one. The browser cookie is unchanged by resend and resolves only the stable parent flow; child challenge IDs remain server-side. Thus, if provider acceptance succeeds but the HTTP response is lost, the browser's existing cookie still resolves the flow's newly active challenge. A stale app-generated code is rejected after promotion, and a cookie for an expired/revoked parent flow cannot act on a later flow.
- Signup-confirmation resend is handled only through Supabase Auth's signup-resend operation. The implementation follows the exact old-code validity and replacement semantics observed in the non-production spike; it does not assume RecallMate's two-phase child-challenge invariant applies to provider-managed signup OTPs.
- The browser receives only an opaque high-entropy parent-flow handle in a cookie with `HttpOnly`, `Secure` on HTTPS, `SameSite=Lax`, `Path=/`, and a short expiry. Its keyed MAC is stored on the parent flow, not on an individual challenge. Before verification, email, password, OTP, access tokens, refresh tokens, and challenge IDs never appear in URLs, logs, returned responses, or cookies/persistent browser storage; email/password/OTP may appear only in the required HTTPS POST body and must never be reflected. After verification, only the normal configured Supabase session cookies may carry session tokens as required by `@supabase/ssr`; email may appear only as the expected signed Auth claim, never in URLs, logs, or reflected output.
- For RecallMate email-step-up only, the database stores an HMAC of `challenge_id || code`, not a plaintext code or an unkeyed six-digit hash. The HMAC key is server-only, versioned, rotatable, and compared in constant time. Supabase signup OTP values are never stored by RecallMate.
- Pending refresh tokens are stored only as authenticated ciphertext (AES-256-GCM or an equivalent reviewed AEAD), with key version/nonce/tag included. Plaintext exists only in server memory for the request and is never logged. The initial access token is discarded after extracting validated claims.
- Parent-flow and child-challenge state is durable and shared across serverless instances. State transitions and attempt increments are atomic. No in-memory map is authoritative.
- Verification locks the parent flow and its active app-generated child challenge, checks flow/challenge status, expiry, attempts and MAC result, and consumes the challenge in one transaction. For an already-ready account, that transaction also writes the verified-session row. For an unready account, it records `stepup_verified_at` and `stepup_verified_pending_enrollment` on the parent flow and writes no verified-session row. That enrollment evidence is usable only within the 10-minute lifetime defined above and while the parent flow and exact pending session remain valid. Concurrent correct submissions can produce at most one successful consumption. Signup-confirmation verification instead follows Supabase Auth's own verification endpoint and does not use this app-generated challenge-attempt transaction.
- Initial delivery creates a `delivery_pending` challenge that is not verifiable. It becomes `code_sent` only after provider acceptance.
- Resend is two-phase. It creates a replacement child challenge as `delivery_pending` while the old `code_sent` challenge remains the parent's active challenge; after provider acceptance, one atomic transition updates the parent's active-challenge pointer, clears its pending pointer, promotes the replacement and marks the old challenge `superseded`. A failed/uncertain send therefore does not strand the user without a valid code, and a lost HTTP response does not strand the browser on a superseded child. Provider acceptance is not represented as proof that the message reached the user's inbox.
- Resend uses provider idempotency where supported. If the send result is uncertain, retries reconcile the same replacement challenge and cannot issue multiple active codes. If the provider cannot guarantee idempotent delivery, the implementation documents its retry semantics and still preserves at most one active challenge after promotion.
- The challenge may be verified only in the active `code_sent` state. No session cookie is issued on delivery or verification uncertainty.
- Challenge create, resend, and verification endpoints are rate-limited by account and IP using a durable server-side limiter (Upstash Redis is the existing candidate dependency). If the limiter is unavailable, challenge creation/verification fails closed. Per-challenge wrong attempts and resend cooldown remain enforced in the database even if Redis is unavailable.
- Auth POST routes validate same-origin/CSRF protections, return `Cache-Control: private, no-store`, and log stable event codes/request IDs only. No code, password, refresh token, email, or raw IP is logged; IP rate-limit keys are keyed hashes.

### Password recovery and change

- Forgot-password responses are neutral regardless of whether the email exists.
- A recovery code/session is processed server-side and never receives `rm_login_verified: true`; it can access only the password-reset operation, not RecallMate data.
- After a successful password reset, the recovery session is revoked and the user must perform a normal password login followed by email step-up. Existing sessions are revoked according to the approved Supabase session policy; recovery is not a login shortcut.
- The hosted Supabase Auth password policy must enforce the 12-character minimum for direct Auth API signup and password change as well as RecallMate forms. Enable leaked-password protection when the project's plan supports it; otherwise document the residual limitation before release.
- Settings supports change-password for password accounts only after the RecallMate app gate and Supabase's own current-password/recent-auth requirement. Google-only accounts may add a password only through a verified, explicit credential-enrollment flow; the UI must not assume every Google user already has a password.
- After password change, the current session is re-evaluated/revoked according to the session policy. Never update a password from onboarding.

### Supabase Auth control-plane boundary

The `rm_login_verified` claim is an authorization contract for RecallMate data and RecallMate-controlled routes. Supabase Auth endpoints such as `/auth/v1/user` are a separate control plane; they do not automatically consult RecallMate's custom claim or Postgres RLS. The design therefore chooses the explicit residual boundary: direct Auth account-management operations are not claimed to be blocked by RecallMate step-up. Product copy and security claims must not imply otherwise.

Inventory and test all Auth operations that can affect identity or credentials: password/email updates, `user_metadata`, reauthentication, password recovery, identity link/unlink, sign-up, OTP, session refresh/revocation, and any future credential enrollment. The required project controls are:

- email confirmation remains enabled;
- secure email change is enabled so both old and new addresses must confirm an address change;
- secure password change/reauthentication is enabled, and RecallMate password changes require `current_password` where supported by the installed SDK plus recent authentication;
- the hosted minimum password length is 12; leaked-password protection is enabled where the project plan supports it;
- security notification emails for password/email changes and identity/factor changes are enabled;
- manual identity linking is disabled unless an explicit product need is approved; if enabled later, its direct Auth API behavior is separately inventoried and tested.

Direct-API acceptance verifies these Supabase controls independently of RecallMate UI: short passwords are rejected by direct signup/change; password change without the configured reauthentication condition is rejected; email change requires the configured old/new confirmations; notification events are emitted; direct identity-link calls follow the configured policy. A successful Auth control-plane operation still cannot create account readiness or a verified RecallMate session. If an operation is not enforceable by Supabase configuration, its residual behavior is documented rather than described as RecallMate-gated.

### Logout, refresh, and session continuity

- Logout revokes the current `recallmate_verified_sessions` row and signs out the Supabase session. Global logout/password-reset revokes every active verification row for that user and Supabase sessions according to the selected session scope.
- Ordinary refresh does not send email. The custom token hook checks the same active `(user_id, session_id)` record and preserves the verified claim only while that record is active.
- If a session or account-readiness record is revoked, sensitive RLS and server-route checks deny new database/API work even if a previously issued JWT has not expired. The claim alone is not treated as immediate revocation.
- Realtime authorization may be cached for an already-open channel until a new JWT is sent or the JWT expires. Logout/revocation must explicitly remove/close local channels and stop processing their events; use a bounded JWT lifetime and test reconnect/new-subscription denial. Do not claim the server instantly terminates every already-open Realtime connection unless the tested Supabase configuration proves it.
- A refresh or cookie-write failure after code verification returns a safe recoverable error and never falls back to an unverified or general session. Finalization is idempotent for the same short-lived opaque flow so a transport retry cannot create a second session or skip claim validation.

## Data and token model

### `private.recallmate_account_readiness`

One authoritative server-only row per Auth user. It is separate from client-writable `public.profiles` and is the only account-enrollment source used by the token hook, RLS helper, and privileged-route guard. Required fields:

- `user_id` primary/foreign key to `auth.users`;
- `status`: `enrollment_required`, `pending`, `policy_reaccept_required`, `ready`, or `blocked`;
- `enrollment_source`: `signup`, `google`, `legacy_reenrollment`, or `external_account`;
- `required_terms_version`, `required_privacy_version`, references to the accepted Privacy and Terms consent events, `profile_ready_at`, `consent_ready_at`, `completed_at`, and audit timestamps.

Only narrow server functions may create/update readiness. A row is `ready` only if the server has validated the username in `public.profiles`, current consent evidence exists, and required identity/email verification completed. Missing rows are treated exactly as `enrollment_required`. A user cannot write readiness through PostgREST, Auth metadata, Storage, RPC, or a service-role route accepting client authority.

### `private.recallmate_legal_consent_events`

Append-only consent audit evidence, unless the full migration audit finds an existing authoritative store that can be safely reused. Required fields are `id`, `user_id`, document kind (`privacy` or `terms`), immutable document version, `accepted_at`, and a server flow/source reference with an idempotency key/uniqueness rule so retries do not duplicate acceptance events. No update/delete grant is given to browser roles. The short-lived pre-signup intent is stored separately and is not considered a finalized consent event until bound to the exact newly created `user_id`.

### `private.recallmate_auth_flows`

One stable parent record per browser-controlled signup or login flow. Required fields:

- `id` UUID primary key and `flow_handle_mac` (unique keyed digest of a high-entropy browser cookie handle);
- nullable `user_id` and `session_id` until the corresponding Auth operation succeeds;
- `primary_method`: `signup`, `password`, or `google`;
- `state`, including `signup_pending`, `challenge_pending`, `stepup_verified_pending_enrollment`, `ready_for_session_issue`, `issued`, `failed`, `expired`, and `revoked`;
- `active_challenge_id` and `pending_challenge_id` child pointers, nullable when no challenge is active/pending;
- `encrypted_refresh_token` nullable until a server-side Supabase session is pending, with key version/nonce/tag; `stepup_verified_at`; sanitized destination; idempotency/request references; and creation/update/expiry timestamps.

The cookie remains stable across resend and contains no child challenge ID. It resolves this parent record through `flow_handle_mac`. Browser requests submit the OTP but never choose the challenge ID; the server selects the active child from the parent flow. For an enrollment-pending flow, the parent keeps the step-up evidence and pending session server-side, but no normal session is issuable until readiness and the verified-session record are committed together.

### `private.recallmate_signup_intents`

Durable, short-lived pre-account data linked by `flow_id` to the parent auth flow. It stores a keyed email digest only for rate limiting/flow matching, username draft, accepted document versions/time, idempotency key, nullable `user_id`, `creation_state` (`pending`, `created_correlated`, `duplicate`, `indeterminate`, `confirmed`, or `expired`), a keyed digest of the flow-specific creation-correlation value, and authenticated ciphertext for same-flow retry; it stores neither a recoverable plaintext email nor a password or OTP. The stable cookie handle belongs only to `recallmate_auth_flows`. Binding is permitted only after the provider contract proves that the exact returned `user_id` carries the correlation issued by this exact parent flow and that duplicate confirmed/unconfirmed creation cannot acquire or overwrite it. A non-null ID, exact-ID lookup, email match, or timestamp alone is insufficient. Correlation material is never an authorization/readiness signal and is erased after successful binding or terminal expiry. Duplicate-account responses never bind to or append consent for an existing user. An indeterminate create/bind failure leaves only an expiring unbound intent and permits safe same-flow retry only with the same correlation; otherwise require the documented recovery path. At OTP verification, the canonical email is reloaded from Auth by this exact bound user ID as specified in the signup flow; the digest is not reversed or used as account identity.

### `private.recallmate_login_challenges`

Each row is a RecallMate-generated email-step-up child-challenge generation belonging to exactly one parent auth flow. Supabase signup confirmation is not stored as a child code challenge; its status remains in the parent signup flow/intent and Supabase Auth owns the OTP lifecycle. Required fields:

- `id` UUID primary key, `flow_id` referencing `recallmate_auth_flows`, and monotonically increasing `generation` unique within the flow;
- `purpose`: `email_stepup`; `delivery_provider`: RecallMate mail;
- `code_mac` for the app-generated code; Supabase-managed signup OTP values are never stored here;
- `status`: `delivery_pending`, `code_sent`, `consumed`, `superseded`, `failed`, `locked`, `expired`, or `revoked`;
- `attempts_used`, `expires_at`, `resend_available_at`, keyed `ip_hash`, request/idempotency key, and creation/update timestamps.

Required indexes cover child lookup by `flow_id`, `(flow_id, generation)`, expiry cleanup, and uniqueness/idempotency constraints. The parent row is the serialization point for verification and resend. At most one email-step-up child is active and at most one replacement is pending per flow. Challenge IDs and the flow handle MAC are never interchangeable. The database stores neither plaintext OTP nor plaintext refresh token. Pending secrets are deleted after successful issuance or terminal expiry/failure.

### `private.recallmate_verified_sessions`

- `session_id` UUID primary key;
- `user_id` referencing `auth.users`;
- `verification_method`: `signup_email_confirmation` or `email_step_up`;
- `primary_method`: `signup`, `password`, or `google`;
- `verified_at`, nullable `expires_at` aligned with the configured Supabase session lifetime, and nullable `revoked_at`.

Invariant: this table contains rows only for sessions whose authoritative account-readiness row is already `ready`. The narrow server transaction that changes readiness to `ready` inserts the corresponding verified-session row atomically. Passing email step-up while enrollment is incomplete records only `stepup_verified_at` on the parent auth flow; it never creates a row here and can never produce `rm_login_verified: true`.

The tables are not browser-readable or browser-writable. The Auth hook receives only the minimum read permission needed; server-only challenge/enrollment operations use narrow privileged functions. Any public-schema RPC facade has fixed/empty `search_path`, fully qualified object references, strict inputs, and `EXECUTE` revoked from `PUBLIC`, `anon`, and `authenticated`; only the required server/Auth roles are granted access. Run Supabase advisors and inspect grants/policies for all auth functions during implementation.

## Token claim and refresh boundary

The Supabase Custom Access Token Hook receives the user, claims including `session_id`, and `authentication_method`; Supabase documents that it runs before token issuance, including token refresh. See [Custom Access Token Hook](https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook) and [User sessions](https://supabase.com/docs/guides/auth/sessions).

Hook behavior is deny-by-default:

1. Preserve Supabase-required claims and the original `aal` unchanged.
2. Set `rm_login_verified` to `false` unless an active account-readiness row is `ready` **and** an active verification row matches both `user_id` and `session_id`, is not revoked, and is not expired.
3. For a match, set `rm_login_verified: true` and `rm_verification_method` to the approved value (`signup_email_confirmation` or `email_step_up`).
4. Ignore `user_metadata` and `public.profiles` alone for enrollment/authorization decisions. Direct `signInWithPassword`, direct Google OAuth, direct `signInWithOtp`, recovery, externally created Auth users, and other auth events remain unverified unless both account readiness and the required flow are completed for that exact session.
5. After a code is atomically consumed and, only for a `ready` account, the matching session row is written, the server must force a refresh using the pending encrypted refresh token. It must validate the refreshed JWT's signature and require the exact configured Supabase project issuer (normally `${SUPABASE_URL}/auth/v1` for a hosted project; use the configured canonical issuer for a custom Auth domain), `aud = 'authenticated'`, `role = 'authenticated'`, numeric unexpired `exp`, expected `sub` and `session_id`, and `rm_login_verified: true`. Only that refreshed session may be written as the browser's Supabase SSR session. An enrollment-pending flow has no verified-session row and cannot pass this issuance check.

The Auth hook must fail closed. Hook/database failure cannot mint a verified claim. The app must test actual event names and signup confirmation behavior in a non-production Supabase project before enabling the hook for production.

## Authorization inventory and enforcement

Before enabling enforcement, produce a checked-in inventory classifying every access path as **public**, **authenticated-and-step-up-required**, or **server-only**. It must include:

- all public-schema tables, views, and materialized views;
- private document, notes, quiz, economy, profile, calendar, and history data;
- Storage buckets and `storage.objects` policies;
- exposed RPCs, especially every `SECURITY DEFINER` function and grants;
- Realtime-enabled tables/subscriptions;
- every API route, Server Action, worker/job endpoint, webhook, and background path;
- every use of `SUPABASE_SERVICE_ROLE_KEY`, every request accepting `userId`, and every retrieval/search function;
- login, signup, OAuth, Calendar integration, logout, and recovery callbacks.
- Supabase Auth control-plane methods reachable with the public key, including direct signup, `/auth/v1/user` password/email/metadata updates, reauthentication, recovery, identity link/unlink, refresh, and provider/configuration behaviors. Each is explicitly labeled public-Auth-control-plane with its platform mitigation and residual; do not imply Postgres RLS or `rm_login_verified` protects the Auth service itself.

Unclassified access is denied until classified. Truly public data is explicitly listed and exempted; it is not inferred from the absence of a policy.

### RLS and Storage

- Every user-private table keeps its current owner/tenant policy and receives an additional **restrictive** policy requiring the active RecallMate verified-session helper. Ownership remains required; a verified claim never grants cross-user access.
- Because browser roles cannot read private readiness/verified-session tables, RLS policies call `private.recallmate_session_is_verified()` with no arguments and a `boolean` return. It is `STABLE SECURITY DEFINER`, owned by a dedicated `NOLOGIN NOINHERIT` `recallmate_authz_reader` role with no `BYPASSRLS`, membership grants, or access beyond `SELECT` on the readiness and verified-session tables. Grant that role `USAGE` on schemas `private` and `auth`, `EXECUTE` on exactly `auth.uid()` and `auth.jwt()`, and `SELECT` only on those two private tables; their internal `SELECT` policies are scoped only to that role. The function derives the user with `auth.uid()` and session/claim values with `auth.jwt()`, requires `rm_login_verified = true`, readiness `status = 'ready'`, and the matching unrevoked/unexpired `(user_id, session_id)` record. It accepts no caller-supplied IDs, sets `search_path = ''`, fully qualifies every object, returns only a boolean, and has no ability to mutate data. Revoke function execution from `PUBLIC`, `anon`, and `service_role`; grant `USAGE` on schema `private` and `EXECUTE` on this exact helper signature to `authenticated`, and grant browser roles no direct privileges on either private table. Validate these grants/policies with catalogs and Supabase advisors.
- For commands with both `USING` and `WITH CHECK`, both predicates enforce the step-up gate. Existing ownership checks remain effective for reads/writes.
- Private Storage buckets use equivalent step-up plus path ownership checks. Public assets remain explicitly public.
- Views must be `security_invoker` where supported or otherwise protected so they cannot bypass underlying RLS. Realtime uses the same table policy boundary.
- RPCs are inventoried individually. User-callable RPCs validate the verified session and ownership; server-only functions have tightly scoped grants. `SECURITY DEFINER` is allowed only when necessary, with fixed empty `search_path`, qualified references, minimal owner privileges, and explicit grants.

### Server/service-role guard

Every service-role route that reads or mutates user data calls one shared `requireVerifiedRecallMateSession()` before creating/using its privileged data client. The guard uses the configured Supabase client's trusted `getClaims()`/JWKS verification path (or an equivalent verified Auth-server signature-validation path for the project's signing-key mode); it never manually decodes an unverified JWT. The expected issuer is resolved server-side from the exact configured project (normally `${SUPABASE_URL}/auth/v1` for a hosted project, or the explicitly configured canonical Auth issuer for a custom domain). Before privileged database work it requires that exact issuer, `aud = 'authenticated'`, `role = 'authenticated'`, numeric unexpired `exp`, nonempty `sub`, `session_id`, and `rm_login_verified === true`, then confirms a `ready` account-enrollment record and active server-side verified-session record for that exact `(sub, session_id)`. It derives the user ID from verified claims and never trusts request `userId`. It rejects before any privileged query, billing, job creation, retrieval, or mutation. Webhooks/background workers use a separate explicit server identity and cannot impersonate a browser user. Tests cover wrong-project issuer, wrong audience/role, expired/missing `exp`, invalid signature, and user/session mismatch.

Middleware and layouts add UX/navigation checks but are not the sole authorization layer. Protected API routes and RLS remain authoritative.

## Cookie and client-session behavior

The stable opaque parent-auth-flow cookie is `HttpOnly; Secure; SameSite=Lax; Path=/`, short-lived, and contains no email/code/token or child challenge ID. Its server-side MAC resolves the parent flow, so resend never requires replacing the browser cookie. Every auth/challenge response is `private, no-store`.

After step-up, the app continues using the normal `@supabase/ssr` browser/server session storage so existing browser Supabase operations can refresh the session. Supabase's SSR guidance expects the browser client to access refresh-token state; an HttpOnly-only final Supabase session would require a separate BFF migration that moves all browser Supabase reads/writes behind server APIs. That larger migration is not part of this design. See [Supabase SSR Advanced Guide](https://supabase.com/docs/guides/auth/server-side/advanced-guide).

No response before successful claim validation may set a Supabase auth cookie, return a token, or return protected application data.

## Error, privacy, and operational behavior

- Wrong email/password: same neutral invalid-credentials response for unknown account and wrong password; no step-up email is sent.
- Successful primary login: neutral verification-required state; no provider details, user ID, or token returned.
- Wrong/expired/previous code: recoverable safe error; wrong attempts increment atomically; five failures lock that challenge.
- Resend: replacement identity remains non-verifiable while delivery is pending; the prior code remains usable until provider acceptance atomically activates the replacement and supersedes the old one. Cooldown and account/IP quotas apply.
- Auth hook, database, limiter, mail provider, or refresh failure: fail closed with a safe unavailable response; never set the normal session cookie and never route into general app access.
- Duplicate signup, username conflict, and email-delivery errors preserve account-enumeration protection. Username availability is UX only; a database unique constraint is authoritative.
- Stable event codes and request IDs support diagnostics. Never log passwords, OTPs, access/refresh tokens, raw email, raw IP, encrypted payloads, or auth request bodies.
- CAPTCHA is supported where configured and is checked server-side; it does not replace rate limits or challenge enforcement.

## Rollout and migration order

1. **Environment prerequisite:** obtain owner-approved access to an isolated non-production Supabase project/branch with Auth, Postgres, Storage, and Realtime. If none exists, stop and request approval before creating a branch/project or incurring cost. No production test users or test documents are created for this work.
2. **Inventory gate:** complete and review the deny-by-default inventory across database, Storage, Realtime, service-role APIs, background work, and the Supabase Auth control plane. Identify public exemptions explicitly.
3. **Non-production spike:** validate installed SDK behavior for server-side password auth, signup confirmation `verifyOtp`, Google PKCE exchange without cookie persistence, hook event names (signup, OTP, OAuth and `token_refresh`), forced refresh, exact claims, and account-enrollment transitions.
4. **Additive schema and platform configuration:** through reviewed migration history, add readiness/consent/challenge/session tables, narrow functions, grants, cleanup, and durable rate-limit configuration. Configure and directly test Auth policy (12-character minimum, email confirmation, secure email/password change, security notifications, and leaked-password protection when plan-supported). This spec stage performs no production mutation.
5. **Implementation in non-production:** implement server auth/parent-flow/child-challenge/enrollment endpoints, pending no-cookie auth, claim refresh/validation, shared service-role guard, logout/recovery, UI, and Auth-control-plane handling. Keep production behavior behind a cutover-controlled mode; never ship a UI-only gate.
6. **Security and acceptance gates:** test direct password/Google/OTP/recovery and direct signup accounts with no readiness row; forged metadata; owner RLS; service-role guard; challenge races/resend; Auth control-plane policy; open Realtime revocation; Google OAuth; Calendar linking; account migration; and browser flows. Finish TypeScript/build/full tests in non-production.
7. **Readiness migration design:** use authoritative consent evidence only. Do not backfill `ready` from `user_metadata`, a `profiles` row alone, or an email-confirmed flag. Classify each existing account; users without current auditable consent/profile readiness become `enrollment_required`. Preserve user IDs and study data. Review the exact backfill and affected-user counts before any production application.
8. **Production preflight (separate owner approval required):** deploy the complete backward-compatible code, additive schema, and hook support while current access enforcement remains unchanged and the new flow is closed to general users. Enter a controlled maintenance/preflight window and allowlist only an owner-approved existing test account. Configure the hook and exercise a complete login/challenge/refresh, proving the refreshed JWT's exact subject/session/claim and `aal` before any production RLS cutover. If the hook, account-readiness check, or refresh smoke fails, do not activate restrictive policies or new-session enforcement; disable the preflight hook, restore normal traffic on the unchanged old contract, and fix the issue in non-production.
9. **Two-phase enforcement cutover (separate explicit owner approval):** once preflight passes, enter maintenance mode that blocks protected app traffic and new interactive login. Activate restrictive RLS/Storage/RPC/Realtime policies and shared service-route guards while traffic remains closed; enable the new auth/enrollment entry flow and revoke old sessions as specified. Run direct-auth denial, verified-session, account-readiness, service-route, and Realtime checks with the approved test account. Do not reopen traffic until all pass. If any check fails, keep maintenance/fail-closed behavior and fix forward; never reopen under old unverified access or remove restrictive RLS as an availability workaround.
10. **Release and monitoring:** after the owner-approved cutover passes, reopen traffic, monitor stable auth-denial, hook, challenge, delivery, and route event codes, and verify support/recovery paths. Production migration/deployment remains outside this design approval.

Existing sessions lacking both an authoritative readiness row and a verified-session record are not grandfathered. They are invalidated/required to reauthenticate during the controlled cutover. Existing email-only users use account recovery to establish a password and complete required enrollment; Google users continue through Google and email step-up. User IDs, profile ownership, and study data are preserved.

## Rollback strategy

- Schema changes are additive. Do not drop challenge/session tables or weaken verified-session policies as an emergency rollback.
- Before the restrictive-policy cutover, a failed production preflight is aborted without changing the old RLS/session contract; remove/disable the unactivated hook and keep the new flow closed.
- After the restrictive-policy cutover, if mail, refresh, hook, readiness, or verification fails, remain in maintenance/fail-closed mode and fix forward. Do not restore normal traffic under a legacy UI or drop/disable RLS to recover availability.
- Do not roll back to a UI/server build that permits passwordless OTP or ignores `rm_login_verified` while restrictive RLS is active. A rollback build must retain the shared server guard and verified-session semantics.
- Do not remove RLS/hook enforcement to restore availability. Any policy rollback that restores unverified access is a security-contract change requiring explicit owner review and a separate risk decision.
- Pending challenge rows expire and are cleaned up after terminal state; verified-session records remain until logout, session revocation, or configured expiry. Retain non-secret security event codes according to the existing log retention policy.

## Acceptance criteria

### Gate 1: direct-auth bypass (must pass before form migration)

- Direct `signInWithPassword()` with the public key can at most obtain an unverified Supabase JWT: private app-table SELECT/INSERT/UPDATE/DELETE, private Storage access, protected Realtime, user RPCs, and service-role-backed user APIs are denied.
- Direct Google OAuth without RecallMate step-up has the same denials.
- Direct `signInWithOtp()` and recovery sessions have the same denials; email OTP alone cannot produce `rm_login_verified: true`.
- Direct public Auth signup, first-time Google sign-in, a legacy OTP account, or an externally created Auth user with no `ready` account-enrollment record cannot gain RecallMate data access, even after otherwise valid primary authentication and email step-up. They must complete the controlled enrollment flow first.
- A signed JWT with absent/false claim, wrong user/session binding, revoked/expired verification row, or user-forged `user_metadata.rm_login_verified=true` is denied.
- Forged `user_metadata.username`, `privacy_agreed`, `recallmate_account_completed`, or equivalent profile flags cannot create account readiness or legal-consent evidence.
- A valid verified JWT is still restricted by the original owner/tenant policies.

### Session and challenge lifecycle

- Correct password creates a server-only pending challenge; no browser Supabase cookie/token or private data is issued before code verification.
- For an already-ready account, correct code is single-use, atomically consumed, tied to the original user/session/provider, followed by server-side refresh, and only the refreshed matching JWT is released. For an unready account, no session is refreshed or released until enrollment commits readiness and the verified-session row.
- For signup OTP verification, tests prove the server calls `getUserById()` only with the exact `user_id` persisted from that flow, verifies the returned ID, uses only the Auth-returned canonical email with `verifyOtp`, and never searches by email or trusts the browser email/digest as identity. A separate creation-correlation test proves an existing unconfirmed Auth user followed by a new RecallMate signup for the same email cannot bind that existing account; returned ID/existence alone is never proof.
- Tests assert the exact refreshed `iss`, `aud = 'authenticated'`, `role = 'authenticated'`, `sub`, `session_id`, `rm_login_verified=true`, numeric unexpired `exp`, valid signature, and unchanged `aal` before cookie issuance; wrong issuer/audience/role, missing or expired `exp`, and invalid signatures fail before privileged access.
- A correct step-up for an account that is not ready consumes the challenge and records `stepup_verified_at` on the parent flow but creates no verified-session row and no verified claim. The enrollment transaction makes readiness `ready` and inserts the verified-session row atomically. Enrollment rejects expired/revoked parent-flow evidence, a mismatched pending `(user_id, session_id)`, and evidence older than 10 minutes; it destroys pending secrets and requires fresh primary authentication and step-up.
- Wrong code increments attempts; the fifth locks the challenge. Expired, stale, superseded, replayed, and concurrent duplicate codes fail safely.
- RecallMate email-step-up resend waits 60 seconds, creates a non-verifiable replacement child while the old app-generated code remains usable, then atomically promotes the replacement in the stable parent flow and supersedes the old child only after provider acceptance. Retry and lost-response tests prove the unchanged browser cookie resolves the new active child and that at most one active code exists. Signup-confirmation resend is tested separately against Supabase's observed provider behavior; no old-code invalidation rule is assumed.
- Refresh preserves verification only for the same active session; unverified sessions remain unverified across repeated refreshes. Logout/revocation blocks RLS and privileged routes.
- Revocation is tested with an already-open Realtime subscription. New joins/refreshes are denied; the app closes local channels immediately on local logout and does not process queued events after a revocation signal. Test the actual remote-revocation cache behavior; if an open connection remains authorized until a new JWT or expiry, document and configure the maximum JWT-expiry exposure bound and require an explicit security sign-off rather than claiming instantaneous remote termination.
- Before verification, no Supabase access/refresh token, normal auth cookie, or protected data is returned to the browser. Email/OTP/password/token values never appear in URLs or logs. After successful verification, only the normal configured Supabase session cookies may carry session tokens/claims; email may be present only as the expected signed post-verification Auth claim, never in a URL or logs.

### Signup, recovery, OAuth, and product behavior

- Signup has username/email/password/confirm/terms; terms start unchecked and are required. Password is created during signup, the signup email code is server-verified, and only then is the verified session issued.
- Login has email/password and sends a RecallMate email step-up after correct primary credentials. The UI keeps neutral account-enumeration-safe responses.
- Google login requires a fresh email step-up for each new session; navigation and token refresh do not resend email.
- Google Calendar linking remains separate, requires an already verified app session, and still completes its existing sync path.
- Password recovery cannot access normal app data; successful reset requires a fresh normal login plus step-up. Settings supports secure change/add-password behavior without onboarding password creation.
- A signup acceptance intent is bound only after exact-ID lookup confirms the flow-specific high-entropy creation correlation and non-production tests prove duplicate confirmed/unconfirmed requests cannot inherit or overwrite it. Non-null IDs, `getUserById()` success, email/timestamp matches, and apparent provider success alone do not prove creation. Duplicate results never bind; indeterminate outcomes remain unbound and take a safe retry/recovery path. Immutable consent events are finalized only after that user's email confirmation and enrollment commit; no failed attempt leaves a finalized orphan consent event.
- The account-readiness record is server-only and is required by token hook, RLS helper, and service-role guard. Existing users without authoritative consent/profile evidence remain enrollment-required until controlled re-enrollment; metadata/profile-only auto-backfill is prohibited.
- Direct Auth API tests and hosted configuration inspection verify the 12-character password policy, email confirmation, secure email change requiring both confirmations, secure password change/current-password or recent-auth requirements, security notification emails, and leaked-password protection when plan-supported. Direct `/auth/v1/user` operations are documented as the separate Auth control-plane residual and are not falsely claimed to be gated by `rm_login_verified`.
- Identity link/unlink calls are rejected when manual linking is disabled; if the product later enables linking, direct API behavior must be re-reviewed and tested.
- Existing `next` sanitization, Privacy/Terms acceptance, accessible error/status announcements, and the RecallMate diamond auth loader remain intact.
- All auth/challenge responses use `Cache-Control: private, no-store`; auth flow and challenge cookies use the defined security attributes.

### Data-path inventory and verification

- The completed inventory has no unclassified table, view, bucket, RPC, Realtime path, service-role route, job endpoint, or user-ID-taking API.
- The production rollout follows the two-phase cutover: all compatible code and schema support are predeployed, the hook/claim path passes controlled preflight before restrictive-policy activation, protected traffic remains in maintenance until RLS, route guards, enrollment and direct-auth denial checks all pass, and old sessions are reauthenticated rather than grandfathered.
- An owner-approved isolated non-production Supabase environment exists and is the only place used for destructive test data, policy mutation, and automated auth/RLS/Realtime tests before release.
- Supabase security advisors and SQL grant/policy review show no unintended `anon`/`authenticated` path to challenge state or auth-only functions.
- Full unit/integration suite, TypeScript, production build, policy tests, authenticated Preview browser tests, password reset, Google OAuth, and Calendar regression pass before production approval.
